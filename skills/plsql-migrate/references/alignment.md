# 業務ロジックとの整合の確かめ方（BIZ 項目）

SKILL.md の Step 6 で、出た BIZ 項目を routine ごとの問いにするときに読む。項目ごとに「移行で何が変わるか」と
「業務文書のどこを探すか」、問いの書き方の例、答えの記録の形がある。項目そのものの定義・聞くこと・記録先は
`docs/plsql-migration/plsql-decisions-outside-generator.md` の §3 にあり、ここでは繰り返さない。

生成コードは Oracle と同じ結果を目指すが、移行先の都合で**意味が変わるところ**がある。実 DB の比較は
シナリオに書いた 1 回の呼び出しを観るだけなので、変わるのが「途中で止まったとき」「同時に書いたとき」
「PL/SQL の外から書いたとき」なら、結果は一致に見える。だから業務の担当者に聞く。

## 読むもの

| 何を | どこに |
|---|---|
| 項目が出た routine | `decision-items.md` の「出た根拠」の欄（routine 名・ファイル名） |
| 元の PL/SQL | `<src>/` の該当 package |
| 生成された本体 | `<out>/src/main/java/<package>/application/<Module>Service.java`。分割した routine は同じ Service の部品の method（`references/operations.md` の「生成物の構成」） |
| 生成された SQL | `<out>/src/main/java/<package>/infrastructure/<Module>Repository.java` |

変わる振る舞いは、項目の一般論ではなく、その routine の業務の言葉で書く
（「1 反復 = 1 トランザクション」ではなく「注文 1 件ずつ締める」）。

## 項目ごとの観点

| ID | 変わる振る舞い（routine の言葉に直して言う） | 業務文書で探す記述 | 食い違いの例 |
|---|---|---|---|
| BIZ-1 | 全体が 1 つの境界ではなくなる。途中で止まると、処理済みと未処理が混ざったまま確定する | 「一括」「全件」「すべて完了してから」「締め」「帳票」「再実行」 | 「締め処理は全件の確定をもって完了とする」「途中の状態を他の業務が参照しない」 |
| BIZ-2 | 対象はページごとに読む。途中で増えた行も処理され、読んでから条件を外れた行は 1 反復の側で確かめないと処理される | 「締めの対象は〜時点の」「基準日」「締め切り時刻」 | 「対象は処理開始時点で確定する」（途中追加を処理してはならない） |
| BIZ-3 | 自律トランザクションの記録は、呼び出し側が別の境界で呼ばない限り、親の失敗で消える | 「失敗しても記録を残す」「監査ログ」「エラー履歴」 | 「失敗した操作も必ず記録する」のに、呼び出し元の一部が同じ境界で呼んでいる |
| BIZ-4 | 行ロックで待つ・弾くのではなく、commit で弾かれる。`NOWAIT` の失敗や `SKIP LOCKED` の「飛ばす」が「弾かれて再試行」になる | 「他の人が処理中なら」「即時に失敗を返す」「取り合い」「先着」 | 「他の担当者が編集中なら即座にエラーを返す」（commit まで分からなくなる） |
| BIZ-5 | MERGE は読んでから挿入か更新を選ぶ。同じキーを同時に書くと片方が弾かれる | 「取り込み」「重複」「同時に」「上書き」 | 「同じ顧客の取り込みが並行して走る」のに、弾かれた側の再試行が無い |
| BIZ-6 | 監査の「誰が」はアプリが渡す利用者になる。照合で補った監査行は書いた主体が `BACKFILL`、時刻が補った時刻で、元の誰が・いつは分からない | 「監査」「内部統制」「変更履歴」「操作者」「法令」 | 「すべての変更に実施者と実施時刻を残す」（補った行は満たさない） |
| BIZ-7 | 上限を超える入力で止まる | 件数の上限（「1 注文あたり」「最大」） | 業務上の上限が設定値より大きい（正当な入力で止まる）。逆に小さいなら食い違いではなく、設定を業務の値に下げる案にする（異常を見逃さないため） |
| BIZ-8 | 一覧に無い表名で呼ぶと実行時に拒否する（Oracle ではどの表でも走った） | 呼び出し側が渡す表名、staging 表の運用 | 一覧に無い表を渡す運用がある |
| BIZ-9 | trigger が掛かるのは生成コードが書く経路だけ。他システム・手作業・ETL の書き込みには掛からない | 対象の表を書く他システム、保守手順、データ移行・一括更新 | 他システムが対象の表を直接更新している（照合で検出される前提か、API を通すかを決める） |
| BIZ-10 | 採番 trigger は、生成コードの INSERT では値として織り込まれるか、採番 Service の呼び出しへの再設計になる。キーを渡さない INSERT は、生成コードの外の経路では採番されない | 「番号の採番」「連番」「欠番」 | 「注文番号は欠番なく連続する」（採番方式の選択に効く） |
| BIZ-11 | タイムゾーンの offset が失われ、同じ瞬間の UTC 表記で読み戻る | 「現地時刻」「どの拠点で」「タイムゾーン」 | 記録時の offset から拠点を読んでいる帳票がある |
| BIZ-12 | TRUNCATE が直前の作業を確定しない | TRUNCATE の前後の手順、「洗い替え」 | TRUNCATE の前の書き込みが確定している前提で、別の処理が並行して読む |

## 答えの 3 つの形

- **受け入れる**: 理由を添える。変わったままになる振る舞いは、変換後の文書の「制限」に残る
- **受け入れない**: 失敗ではない。その routine の設計を変える判断材料である（分割をやめる、行ロックを残す別の方式に
  する、呼び出し側で補う）。`limits.yaml` の決定で済むこともある（分割をやめる = `transactions.perIteration` から
  外す）が、再設計になることもある。どれを選ぶかは利用者が決める
- **担当に確認する**: 利用者が業務担当でなければ、この形になる。案と食い違いだけを記録し、決定にしない

## 業務文書との食い違い

業務文書と生成物の振る舞いが食い違ったら、それは確認ではなく**再設計の要否**の問題である。案にせず、食い違いとして
記録して報告する。

食い違いの原因が移行ではなく**元の PL/SQL** にあることもある（例: 仕様は「全件一括で確定」だが、PL/SQL が 100 件ごとに
中間コミットしている。仕様は「出荷済み」だが、PL/SQL は受注日で絞っている）。これは移行で生じた差ではない。
食い違いの記録に「移行前から」と明記し、移行で変わった部分と分けて書く。直すかどうかは業務側の判断で、移行の作業に
含めるかも利用者が決める。

## 問いの書き方の例

routine 名・エラーコード・状態の値は形を示すためのもので、実際の問いでは原文と生成物から取る。

**BIZ-1 / `prc_nightly_close`**

> 変わること: Oracle では出荷済みの注文を 100 件ごとに中間コミットしていました。移行後は 1 件ずつ
> 確定します（1 件 = 1 トランザクション）。途中で止まったときに確定済みと未処理が混ざるのは同じですが、
> 境目が 100 件単位ではなくなります。再実行すると未処理の分だけ締めます（締め済みは `CLOSED` になり、
> 対象の条件 `status = 'SHIPPED'` から外れるため）。`batch_control` を `FAILED` にする処理は
> `prcNightlyCloseFailedBatch` として分かれ、呼び出し側が呼ぶまで書かれません。
> 聞きたいこと: 境目が 100 件単位であることに頼っている帳票や後続処理はありますか。途中で止まったことを
> 誰がどう知りますか（CALL-2）。

**BIZ-4 / `pkg_stock_reserve.reserve_nowait`**

> 変わること: 在庫を引き当てるとき、他の人が同じ商品を処理中でも待たずに進み、commit のときに
> 衝突が分かります。Oracle では即座に -20031 を返していました。
> 聞きたいこと: 「処理中なら即座に断る」ことに業務上の意味（画面で待たせない、別の倉庫へ回す）がありましたか。

## 記録

記録は `decision_items.py set <ID> --record <record.yaml> …` で書く（SKILL.md の Step 5）。BIZ 項目の答えは次の形にする。

| 答え | `set` の引数 |
|---|---|
| 業務文書から読み取った答え（決定ではない） | `--status 未決 --proposal "<案>（出典: <文書> <節>）"` |
| 受け入れた | `--status 決定 --decision "受け入れる: <理由>" --by <役割> --date <YYYY-MM-DD> --where <記録先>` |
| 受け入れない | `--status 決定 --decision "受け入れない: <どう直すか>" --by … --date … --where …`。直し方（`limits.yaml` の変更、呼び出し側の対応、再設計の issue）を報告の「次の手」に入れる |
| 業務文書と食い違う | `--status 未決 --conflict "<食い違い>（出典: <文書> <節>）"`。元の PL/SQL にすでにある食い違いは「移行前から」と書く |

1 項目に routine が複数あって答えが分かれるときは、`--decision` に routine ごとの答えを並べて書く。
