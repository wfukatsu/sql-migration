# 変換できない文の対応案・SELECT の並列取得・H2 の索引のデメリット

作成日: 2026-09-15
関連文書: `docs/dml-benchmark-report.md`（DML テスト SQL の変換とベンチマーク）、`skills/sql-transpile/references/scalardb-grammar.md`（変換ルール）

## 結論

- **変換できなかった書き込みの大半（14 文）は「書き込み計画」で自動化できる。** 読み取りの実行計画と同じく対象行を ScalarDB から読み、H2 で新しい値と主キーを計算し、主キー指定の書き込みを同じトランザクションで行う。1 行の更新は約 2.3 倍（16 → 36 ms）、約 1,000 行では 1.7 秒で、数百行を超える一括更新は分割が要る
- **変換ツールの書き換えだけで直せる文もある（4 文）。** Oracle の `INSERT ALL`、`DEFAULT`、現在時刻、`RETURNING`。採番（IDENTITY・シーケンス）と `SAVEPOINT` はアプリの設計が要る
- **表を読む SELECT の並列取得は、この環境では 1.2〜1.3 倍しか速くならない。** 3 表を並列に読んでも、1 表を範囲で 8 分割しても同程度。並列にすると表ごとに別のトランザクションになり、1 つのスナップショットで読めなくなる代償も大きい
- **キーを指定した読み取りの並列化は効く。** 100 キーでは 108 → 49 ms（2.2 倍）。1,000 キーでは 1.3 倍
- **並列化より `scan_fetch_size` を 10 から 1000 にするほうが効く。** 5 万行の取得が 1,264 → 649 ms（1.9 倍）、S04 の 3 表が 1,207 → 801 ms（1.5 倍）
- **H2 の索引のデメリットは、構築時間とメモリ。** 構築時間は投入と同程度で、1 表だけの文には純粋な追加になる（100 万行規模で +0.2 秒、+19〜50%）。索引で H2 のメモリが約 1.6 倍になる。結合を含まない計画では索引を作らないようにするべき

## 1. 変換できなかった文の対応案

### 1.1 分類

`skills/sql-transpile/examples/dml/` の各 51 文のうち、ScalarDB への変換が ERROR になった文（Oracle 19、PostgreSQL 19、MySQL 18）を、直し方で 3 つに分けた。

| 分類 | 文 | 直し方 | 自動化 |
|---|---|---|---|
| A. 変換ツールの書き換え | I03（Oracle の `INSERT ALL`）、I05（`DEFAULT`）、I06（現在時刻）、D09（`RETURNING`） | ScalarDB SQL の文に書き換える（1.2） | 変換ツールで可能 |
| B. 書き込み計画 | U04・U05・U06・U07・U10・U11、D05・D06・D07・D08、I04・I09・I11・I12、MySQL の U11・D08（`ORDER BY ... LIMIT`） | 読む → H2 で計算 → キーで書く（1.3） | 実行基盤の拡張で可能 |
| C. 設計が要る | I07（IDENTITY / AUTO_INCREMENT）、I08（シーケンス・採番表）、T01（`SAVEPOINT`）、`audit_log` の表定義 | 採番の方式、トランザクションの組み立てを変える（1.4） | 不可 |

ScalarDB Cluster で実際に拒否されることも確かめた（`DB-SQL-10026: Syntax error`）: `SET qty = qty - 5`、`IN (SELECT ...)` の DELETE、`INSERT ... SELECT`。`SET qty = 45`（リテラル）は受け付けられる。

### 1.2 A: 変換ツールの書き換えで直せる文

| 文 | 書き換え | 注意 |
|---|---|---|
| I03 Oracle `INSERT ALL INTO t VALUES (...) INTO t VALUES (...) SELECT * FROM dual` | 行ごとの `INSERT`（同じ表なら `VALUES (...), (...)`） | 表が違う `INTO` は文を分ける。条件付き `INSERT ALL WHEN ...` は B に回す |
| I05 `VALUES (..., DEFAULT, ...)` | 表定義の `DEFAULT` の値をリテラルで埋める。列を省いた INSERT も同様に補う | DDL か `--schema` で既定値が分かる場合だけ。ScalarDB の表には既定値が無いので、分からなければ ERROR のまま |
| I06 `SYSTIMESTAMP` / `CURRENT_TIMESTAMP` / `NOW()` | バインド変数 `?` にし、アプリが時刻を渡す（レポートに「時刻をバインド」と出す） | 時計とタイムゾーンが DB サーバーからアプリに変わる（`app-side-notes.md` の `SYSDATE`） |
| D09 `DELETE ... RETURNING cols` | 同じトランザクションで `SELECT cols ... WHERE <同じ条件>` → `DELETE` | 条件が主キーでない場合は B と同じく読んだ行のキーで消す |

### 1.3 B: 書き込み計画（読む → H2 で計算 → キーで書く）

読み取りの実行計画の仕組み（ScalarDB から取得し、H2 で元の SQL を実行）を書き込みに広げる。

1. **取得**: 対象の表と、SET・WHERE・副問合せが参照する表を、実行計画と同じく取得する（WHERE のうち ScalarDB で絞れる条件は押し下げる）
2. **計算**: 元の DML を、主キーと新しい値を返す SELECT に書き換えて H2 で実行する

   | 元の文 | H2 で実行する SELECT |
   |---|---|
   | `UPDATE stock SET qty = qty - 5 WHERE warehouse_id = 1 AND product_id = 103` | `SELECT warehouse_id, product_id, qty - 5 AS qty FROM stock WHERE warehouse_id = 1 AND product_id = 103` |
   | `UPDATE orders o SET total = (SELECT SUM(...) FROM order_items i WHERE i.order_id = o.order_id) WHERE ...` | `SELECT o.order_id, (SELECT SUM(...) ...) AS total FROM orders o WHERE ...` |
   | `DELETE FROM orders WHERE NOT EXISTS (SELECT 1 FROM order_items i WHERE ...)` | `SELECT order_id FROM orders WHERE NOT EXISTS (...)` |
   | `INSERT INTO audit_log (...) SELECT ... FROM orders WHERE status = 'CANCELLED'` | そのままの `SELECT ...` |
   | `INSERT ... ON CONFLICT (k) DO UPDATE SET qty = stock.qty + EXCLUDED.qty` | `SELECT qty FROM stock WHERE k = ...`。あれば `UPDATE`、無ければ `INSERT` |
   | `INSERT ... ON CONFLICT DO NOTHING` / `INSERT IGNORE` | 主キーで読み、無ければ `INSERT` |

3. **書き込み**: 返った行ごとに、主キーを指定した `UPDATE` / `DELETE` / `INSERT` をバインド変数で発行する
4. **COMMIT**: 1〜3 を 1 つの ScalarDB トランザクション（読み取り専用ではない）で行う

**正しさ。** Consensus Commit は、読んだレコードを書くときに、ほかのトランザクションの更新と衝突すれば COMMIT で失敗させる。このため `qty = qty - 5` の更新が失われることは無い。ただし D06（明細の無い注文を消す）のように「無いこと」を条件にする文は、読んだ後に明細が追加されても衝突にならない。このような文を正しく扱うには `SERIALIZABLE` が要る（本検証のクラスタは `SERIALIZABLE`）。`SNAPSHOT` では、計画にその旨の警告を付ける。

**順序に依存する文。** U11・D08（`ORDER BY ... LIMIT 1`、`ROWNUM`）は、並びの値が同じ行がどれになるかが DB によって違う。書き込み計画では H2 の順序になるので、主キーを並びの最後に加えて決定的にする。

**コスト（ScalarDB Cluster で実測、各 9 回の p50）:**

| 処理 | 行数 | p50 |
|---|---|---|
| リテラルの UPDATE（変換できる U01 の形） | 1 | 15.6 ms |
| U04 を読む → UPDATE に書き換え | 1 | 35.8 ms |
| 4 注文の明細をキーで読む → 各行をキーで UPDATE | 9 | 94.9 ms |
| 40 注文の明細 | 100 | 405.7 ms |
| 400 注文の明細 | 988 | 1,726.7 ms |

- 1 行の更新は、読み取りが加わって約 2.3 倍になる
- 行数が増えると 1 行あたり 1.7〜10 ms で、数百行を超える一括更新（D05・D07 のように条件に合う行をすべて消す文）は 1 回の要求としては重い。キーの範囲ごとにトランザクションを分けるバッチ処理にするか、`ROW_LIMIT` を超えたら ERROR にする
- この計測は ScalarDB Cluster の再起動直後で、`docs/dml-benchmark-report.md` の書き込み（3〜6 ms）より遅い。比べられるのは同じ回の値どうし

**実装箇所。** `decomposer.py` に DML 用の分解（対象表の主キーと SET の式を射影する SELECT を作る）を加え、`runtime-java` に書き込み用の実行（H2 の結果を主キー指定の書き込みにする）を加える。読み取りの実行計画の取得・H2・索引の仕組みはそのまま使える。

### 1.4 C: 設計が要る文

| 文 | 対応案 |
|---|---|
| I07 IDENTITY / AUTO_INCREMENT、`audit_log` の表定義 | 主キーをアプリで作る。UUID・ULID（`TEXT`）が最も簡単。数値が要るなら下の I08 のブロック採番 |
| I08 シーケンス（MySQL は採番表） | 採番表を 1 行ずつ `next_val + 1` で更新すると、同時実行ですべての書き込みがその 1 行で衝突する。アプリの各インスタンスが 1 回のトランザクションで 1,000 件などの範囲を確保し、メモリ上で配る（ブロック採番）。欠番と順序の逆転は許容する |
| T01 `SAVEPOINT` | ScalarDB にはセーブポイントが無い。途中の失敗を部分的に取り消す処理は、検証を書き込みの前に済ませる形に組み替えるか、トランザクション全体を再実行する |

### 1.5 変換はできたが ScalarDB で失敗した文

変換ツールの判定が OK / WARN / PLANNED なのに失敗した文は、`docs/dml-benchmark-report.md` 4.2〜4.6 のとおりで、いずれも変換ツールで直せる: H2 の予約語の別名を引用符で囲む（S11）、`NULLS LAST` を含む `ORDER BY` を実行計画に回す（S12）、PostgreSQL の `DATE '...'` / `TIMESTAMP '...'` を文字列にする（I01・U02）、MySQL の `TRUE` / `FALSE` を INT 列では `1` / `0` にする（I01・I02・I10・S16）、MySQL の照合順序の差を警告する（S10）。

## 2. SELECT の並列取得

### 2.1 現状

`Runner.run`（`runtime-java/.../Runner.java:57`）と `Bench.planRun` は、1 つの読み取り専用トランザクションの中で、計画の取得を順に実行し、取得のたびに H2 に投入する。計画の取得は表ごとに独立しているので、並列にすること自体はできる。

### 2.2 並列にするときの制約

- **トランザクションを分ける必要がある。** ScalarDB の `SqlSession` とトランザクションはスレッドセーフではない（公式の SQL API ガイド）。並列に読むには、スレッドごとに接続とトランザクションを持つ
- **1 つのスナップショットで読めなくなる。** 表 A と表 B を別のトランザクションで読むと、その間にコミットされた更新の前後が混ざる。例: 注文の合計と明細を並列に読むと、両方を更新するトランザクションの前の注文と後の明細を結合しうる。元の DB でも ScalarDB の 1 トランザクションでも起きない結果になる。1 つの表を範囲で分けて読む場合も同じ
- **並列にしてよいのは、** 更新がほとんど無い表（マスタ）を読む場合、互いに無関係な表を読む場合、多少の不整合を許すレポートに限られる。計画に `parallel_fetch: true` のような明示的な指定を設け、既定は今のまま（1 トランザクション）にする
- **同時実行時は資源を奪い合う。** 1 要求が N 本の接続と ScalarDB Cluster のスレッドを使うので、同時要求が多いと全体のスループットは上がらない

### 2.3 計測

S04 の 3 表（顧客 2,006、注文 14,974、明細 50,009 行）を、ScalarDB SQL の JDBC で読んだ（ウォームアップ 2 回 + 7 回の p50）。ScalarDB Cluster のノード側の `scalar.db.scan_fetch_size` を既定の 10 と 1000 で比べた。

| 読み方 | fetch size 10 | fetch size 1000 |
|---|---|---|
| 明細だけ | 1,264 ms | 649 ms |
| 3 表を順に、1 トランザクション | 1,207 ms | 801 ms |
| 3 表を並列に、3 トランザクション | 1,024 ms（1.18 倍） | 647 ms（1.24 倍） |
| 明細を order_id の範囲で 2 分割して並列 | 993 ms | 654 ms |
| 同 4 分割 | 1,116 ms | 533 ms |
| 同 8 分割 | 823 ms（1.28 倍） | 795 ms（ばらつき大） |
| 同 4 分割を順に、1 トランザクション | 1,068 ms | 747 ms |

明細（主キー order_id, line_no）を、パーティションキーで 1 件ずつ読む場合（キーを渡される結合、Cassandra の key feed）:

| キー数 | 順に、1 トランザクション | 4 並列 | 8 並列 |
|---|---|---|---|
| 100（246 行） | 108 ms | 57 ms | 49 ms（2.2 倍） |
| 1,000（2,489 行） | 1,216 ms | 1,069 ms | 920 ms（1.3 倍） |

- **表を読む取得は、並列にしても 1.2〜1.3 倍。** 分割を増やしても伸びず、8 分割はかえって不安定になった。1 台の ScalarDB Cluster ノードとバックエンドの PostgreSQL（同じマシンの Docker）が律速している。本番の複数ノード構成では伸びる可能性があり、そこで測り直す必要がある
- **範囲の条件はバックエンドに押し下げられている。** 4 分割を順に読んでも全体を 1 回読むのと同程度で、各範囲が表全体を読んではいない
- **キーごとの読み取りは、往復の回数が律速なので並列化が効く。** ただしキーが多いと ScalarDB Cluster 側が律速し、効果は小さくなる
- **`scan_fetch_size` を 1000 にするだけで 1.5〜2.4 倍。** 並列化より効き、トランザクションも分けずに済む。計画の `recommended_config` は既に 1000 を推奨している。キーを指定した短い読み取りが遅くならないかは確かめる必要がある（以前の検証では既定のほうがわずかに速かった）

### 2.4 推奨

1. **ノード側の `scalar.db.scan_fetch_size` を 1000 程度にする。** 最も効果が大きく、整合性を変えない。キー指定の読み取りと書き込みで回帰が無いか、ベンチマークで確かめる
2. **キーごとに読む取得（key feed、IN リスト）だけ並列化する。** 1 つの取得の中の往復を並列にする。同じ文の結果が 1 つのスナップショットに揃わない点は同じなので、計画に明示的に指定したときだけ行う
3. **表を範囲で分けて並列に読むのは、今は採用しない。** この環境での効果が小さく、整合性の代償が大きい。複数ノードの ScalarDB Cluster で測ってから判断する
4. **取得と H2 への投入を別スレッドにする（1 トランザクションのまま）。** 投入は 6 万行で約 50 ms（3.1 の計測）で、取得の 1 割未満なので効果は小さい。優先度は低い
5. **根本的には読む行数を減らす。** 集計表、キーで絞れる設計、分析系の問合せは ScalarDB Analytics に回す

## 3. H2 の索引のデメリット

### 3.1 計測

`Residual` を直接使い、S04 相当の表（顧客・注文・明細、明細は注文あたり 0〜4 行）を 4 つの規模で生成して、投入・索引の構築・問合せの時間（3 回の最小）と、H2 が持つヒープを測った。ScalarDB からの取得は含まない。

| 注文 / 明細 | 文 | 索引なし 合計 | 索引あり 投入 + 構築 + 問合せ = 合計 | 差 |
|---|---|---|---|---|
| 5,000 / 9,767 | S08 1 表の集約 | 29 ms | 22 + 7 + 5 = 34 ms | +5 ms |
| | S03 OFFSET | 25 ms | 15 + 4 + 0 = 19 ms | 同程度 |
| | S04 3 表結合 | 1,086 ms | 13 + 12 + 14 = 39 ms | 28 倍速い |
| | S05 反結合 | 1,096 ms | 13 + 11 + 3 = 27 ms | 41 倍速い |
| 20,000 / 40,378 | S08 | 29 ms | 16 + 12 + 7 = 35 ms | +6 ms |
| | S03 | 23 ms | 16 + 11 + 0 = 27 ms | +4 ms |
| | S06 相関副問合せ | 1,174 ms | 51 + 47 + 2 = 100 ms | 12 倍速い |
| 100,000 / 201,050 | S08 | 166 ms | 84 + 52 + 46 = 182 ms | +16 ms（+10%） |
| | S03 | 94 ms | 86 + 50 + 0 = 136 ms | +42 ms（+45%） |
| | S04 | — | 260 + 285 + 332 = 877 ms | |
| 500,000 / 1,000,842 | S08 | 893 ms | 431 + 306 + 327 = 1,064 ms | +171 ms（+19%） |
| | S03 | 480 ms | 427 + 291 + 0 = 718 ms | +238 ms（+50%） |
| | S04 | — | 1,580 + 1,801 + 2,045 = 5,426 ms | 構築が 1/3 |
| | S05 | — | 1,422 + 1,755 + 378 = 3,555 ms | 構築が半分 |

— = 索引なしの結合は総当たりで時間がかかりすぎるため測っていない（2 万注文で 23〜28 秒、`docs/dml-benchmark-report.md`）。

H2 のヒープ（3 表を投入した状態）:

| 注文 / 明細 | 行の分 | 索引の分 |
|---|---|---|
| 5,000 / 9,767 | 6.4 MB | +1.2 MB（+19%） |
| 20,000 / 40,378 | 8.8 MB | +4.8 MB（+55%） |
| 100,000 / 201,050 | 42 MB | +24 MB（+57%） |
| 500,000 / 1,000,842 | 208 MB | +118 MB（+57%） |

### 3.2 デメリット

1. **構築時間は投入と同程度で、行数に比例する。** 結合のある文では、総当たりを避ける効果がはるかに大きい。ただし 100 万行規模では構築が全体の 1/3〜1/2 を占める
2. **1 表だけの文には純粋な追加になる。** 今の `decomposer._index_columns` は、結合が無くても主キーを取得していれば主キーの索引を作る。S08・S03 のような文では索引が使われず（S03 は ORDER BY に使われるが、構築の分を取り戻せない）、100 万行規模で +0.2 秒（+19〜50%）。今回のベンチマークの S03・S07・S08 の 30〜40 ms の増加もこれ
3. **メモリが約 1.6 倍になる。** H2 はメモリ上のデータベースで、要求ごとに作る。同時に 10 要求が 100 万行規模の計画を実行すると、索引だけで 1 GB を超える。JVM のヒープと、計画の行数上限（`ROW_LIMIT`）はこの分を見込む必要がある
4. **作れなかった索引に気づけない。** `Residual.ensureIndexes` は失敗した `CREATE INDEX` を黙って飛ばす。列名の違い（取得していない列、引用符が要る名前）で索引が作られないと、結果は正しいまま数十秒かかる
5. **索引が効かない結合がある。** H2 の結合は入れ子ループで、ハッシュ結合が無い。式を使う結合（`ON UPPER(a.x) = b.y`、型の違う列の比較）、複合索引の 2 番目以降の列だけでの結合では索引が使われず、総当たりに戻る。重複の多い列（`status`・`region`）での結合も、索引の効果は小さい
6. **構築は最初の問合せのときに 1 回だけ。** その後に投入した表には索引が作られない。今の `Runner` はすべて投入してから 1 回だけ問い合わせるので起きないが、`Residual` を複数の問合せで使い回すと起きる

### 3.3 対策案

| 対策 | 箇所 | 効果 |
|---|---|---|
| 結合・相関・IN 副問合せの無い計画では、主キーの索引も作らない | `decomposer._index_columns` | 1 表の文の +30〜40 ms（100 万行で +0.2 秒）が無くなる |
| 行数の少ない表（例: 1,000 行未満）には作らない | `Residual.ensureIndexes`（投入した行数で判断） | 小さなマスタ表の無駄な構築を省く |
| 作った索引・作れなかった索引と構築時間を `stats` に出す | `Residual`・`Runner`・`Bench` | 索引の失敗と、構築の割合が見える |
| `indexed` を表ごとにし、後から投入した表にも作る | `Residual` | 使い回したときの取りこぼしを防ぐ |
| 式の結合を計画の段階で警告する | `decomposer._join_columns` | 総当たりになる計画を事前に知らせる |
| 計画の行数上限の既定値を、索引込みのメモリで見積もる | `decomposer`・`appside.estimate_cost` | 同時実行時のメモリ不足を防ぐ |
