# 実案件の PL/SQL を corpus に入れるときの匿名化の方針

[文書の入口](../README.md) ｜ [KPI](plsql-kpi.md) ｜ [実装計画](plsql-conversion-implementation-plan.md) ｜ [corpus](../../fixtures/plsql/README.md)

2026-09-20 の決定（Issue #15）。実案件のコードを corpus に足して KPI を出自別に出すための、前提の決まりです。**道具は「置き換える」ところまでで、「公開してよい」と判断するのは人です。**

## 1. 決めたこと

| | 決定 | 理由 |
|---|---|---|
| 何を置き換えるか | **名前、リテラル、コメントの全部**（下の 2） | 顧客を特定できるものを残りにくくする。名前とコメントだけでは、リテラルに入った顧客名・コード体系・金額の閾値が残り、人の確認が重くなる |
| 元のコード | **このリポジトリに入れない。** 置き場所は、顧客との取り決めに従う場所 | リポジトリは GitLab と GitHub の両方に出る |
| 対応表（元の名前 → 置き換え後） | **このリポジトリに入れない。** 元のコードと同じ場所に置く。道具は、リポジトリの中への書き出しを拒む | 対応表は、匿名化を元に戻す鍵である |
| 期待判定（AUTO / REVIEW / REDESIGN）と理由 | **匿名化の前に、元のコードを読んで付ける。** 理由の文は、匿名化後の名前で書く | 匿名化すると業務上の意味が読めなくなる。期待判定を、ツールの出力を見る前に決めるのは holdout と同じ規律 |
| 出自の記録 | `manifest.yaml` の `origin: real-anonymized`。実案件の unit は、**入れた時点で holdout（独立）** として扱う | 実案件のコードは、ルールを書いた人が見ていない。いちばん強い holdout になる（[corpus の README](../../fixtures/plsql/README.md)） |
| 数字を出す時期 | 仕組みは先に作る。**実案件の数字を出すのは、判定者（Issue #6）が決まってから** | 数字が動いたあとで判定者と基準を決めると、基準を数字に合わせたのか、基準に照らして数字を見たのかを区別できない |
| 最後の確認 | **人が、匿名化後のコードを全部読んでからコミットする** | 道具はトークンを置き換えるだけで、意味は分からない（下の 4） |

## 2. 何が置き換わり、何が残るか

`python -m plsql.anonymize` が行うこと:

| | 置き換える | 残す |
|---|---|---|
| 名前 | スキーマ、テーブル、列、routine、変数、ラベル、ファイル名 → `n0001` の形。同じ名前は、大文字小文字を問わず、全ファイルで同じ置き換えになる | Oracle のもの: キーワード、事前定義の例外（`NO_DATA_FOUND`）、擬似列（`NEXTVAL`、`ROWNUM`）、組み込み関数、`DBMS_` / `UTL_` / `SYS_` などで始まるパッケージとそのメンバー。慣習の接頭辞（`p_`、`v_`、`pkg_`）。`schema.sql` というファイル名 |
| 文字列リテラル | 同じ長さのダミー。同じリテラルは同じダミーになる（`status = 'X'` が INSERT した値と比べられる関係は保たれる）。**動的 SQL の文字列は、SQL として匿名化する**（キーワードは残り、中のテーブル名は置き換わる） | 日付と数値の書式（`'YYYY-MM-DD'`、`'FM999,990.00'`）、空文字列 |
| 数値 | 閾値、率、件数などの数値 | 0〜10、型の大きさ（`VARCHAR2(100)`、`NUMBER(12, 2)`）、アプリケーションのエラーコード（-20000〜-20999） |
| コメント | 全部消す（ヒントも含む） | 改行。行番号は動かない |

キーワードでもある一般的な英単語（`cancel`、`purge`、`summary` など）を名前に使っている場合、字句解析器はそれをキーワードとして読むので、置き換わりません。顧客を特定する語ではありませんが、人が読むときに気に留めてください。

## 3. 匿名化しても、ツールの結論が変わらないこと

匿名化した結果で測った KPI が、元のコードについての数字であるためには、**匿名化の前後で解析の結論が同じ**でなければなりません。道具は、両方のツリーを解析して、routine ごとに次を比べます（名前とリテラルは比べるものに入っていないので、比較の結果そのものは元のコードについて何も言いません）。

- routine の種類、引数と宣言の数
- 原文の文のそれぞれについて、種類、SQL の種類、読むテーブルと書くテーブルの**数**、ロック、診断のコード
- トランザクションの効果（COMMIT / ROLLBACK / SAVEPOINT / 自律）、動的 SQL の有無
- 効いたルールの id と、証拠の無い段階の判定

違いが出たら、終了コードが 1 になります。原因は 2 つのどちらかで、どちらも人が見る必要があります。

1. **Oracle のものである名前を置き換えた。** `--keep NAME` で残す。実際に corpus で起きた例: `DBMS_ASSERT.SIMPLE_SQL_NAME` を置き換えたら、解析が「解析した範囲に無い routine の呼び出し」と見て、元には無かった `CALL-001` が効いた。これを受けて、`DBMS_` などで始まるパッケージとそのメンバーは一律に残すことにした
2. **ルールが「何と呼ばれているか」に依存している。** これはルールについての発見である。実案件のコードは、同じものを別の名前で呼ぶ

合成 corpus の 67 routine 全部で、名前 221・リテラル 45・数値 10 を置き換えても、この比較に違いが出ないことを、テストが押さえています（`tests/test_plsql_anonymize.py`）。つまり、いまのルールは名前に依存していません。ルールを足してこのテストが落ちたら、そのルールは名前を見ています。

## 4. 道具が約束できないこと

道具はトークンを置き換えるだけで、意味は分かりません。次のことは、人が読んで判断します。

- **構造そのものが顧客を特定しないか。** 列の並び、テーブルの数、業界に特有の処理の形
- **残したものの組み合わせ。** エラーコードの体系、型の大きさの並び、キーワードでもある名前
- **置き換え漏れ。** 道具は、元の名前とリテラルが出力に残っていないかを調べて、残っていれば場所を言います（置き換え後の名前で言い、元の名前は出力しません）。これは読む範囲を狭めるためのもので、読むことの代わりではありません
- **匿名化しても入れてよいか。** 契約と、顧客の了解

## 5. 手順

```bash
# 1. 元のコードを読んで、routine ごとの期待判定と理由を決める（ツールの判定を見る前に）
# 2. 匿名化する。元のツリーには書き込まない。対応表はリポジトリの外へ
.venv/bin/python -m plsql.anonymize /secure/customer-x/src \
    --out fixtures/plsql/src/real/<unit のディレクトリ> \
    --mapping-out /secure/customer-x/mapping.json
#    終了コード 0: 匿名化でき、解析は変わらない / 1: 違いか、残った名前がある（まだコミットしない） / 2: 何も書いていない
# 3. 匿名化後のコードを、人が全部読む
# 4. manifest.yaml に unit を足す: origin: real-anonymized、holdout: true、期待判定と理由（匿名化後の名前で）
# 5. 判定者が決まってから（#6）、出自別の数字を出す
.venv/bin/python -m plsql.kpi
```

`python -m plsql.kpi` は、parse 率・判定一致・compile 率・意味的同等性・リスク密度を、全体に加えて**出自別**（合成 / 実案件）と**証拠の独立性別**（独立した holdout / 参照済みの holdout / 開発用）に出します。実案件が 1 件も無いうちは、その行を「0 unit — まだ測っていない」と出します。

## 6. いまの現在地（2026-09-20、合成 corpus だけ）

| | unit / routine | 判定一致 |
|---|---|---|
| 全体 | 29 / 67 | 95.5%（64/67） |
| 独立した holdout（`holdout2/`） | 4 / 8 | 62.5%（5/8） |
| 参照済みの holdout（`holdout/`） | 5 / 10 | 100%（10/10） |
| 開発用 | 20 / 49 | 100%（49/49） |

**この 62.5% を、「ルールが未知のコードで 4 割外す」と読んではいけません。** 食い違う 3 件は、どれも `holdout2/` の `pkg_shipment`（`is_shippable`・`line_count`・`days_in_transit`）で、期待値が REVIEW、判定が AUTO です。原因は、期待判定を固定した**あと**で判定の方針が変わったこと（2026-09-20: REVIEW は移行の可否が未解決のときだけ）で、AUTO 禁止条件の取りこぼしではありません。holdout の期待値は書き換えない決まりなので、食い違いのまま数えています（[corpus の README](../../fixtures/plsql/README.md)、[KPI](plsql-kpi.md) の KPI-3）。

それでも、分けて出す意味は 2 つあります。

- **どの数字が自己採点かが、報告の上で見える。** 開発用と参照済みの 100% は、ルールと期待判定を同じ人が突き合わせながら書いた結果です。独立した証拠は 8 routine しかなく、1 つの package の 3 件で 37.5 ポイント動きます。これまでは、この区別はテストと README の中にしかなく、`python -m plsql.kpi` の出力には全体の 1 つの数字しか出ていませんでした
- **実案件のコードは、独立した holdout と同じ条件になる。** 期待判定を人が先に決め、ルールはそのコードを見ていません。方針の解釈のずれも含めて、食い違いはこの行に出ます。だから実案件の数字は、全体に混ぜず、この行と並べて読みます
