# PL/SQL 移行: 生成コードの外で決めること

PL/SQL を変換するとき、生成器は**決めてよいことだけ**を決め、それ以外は生成物の中に「ここは人が決める」と
残す（計画 §9、`limits.yaml` の「決めたと書けるのは、決めた人がいるときだけ」）。この文書は、その**残された
問い**を 1 か所に集めたものである。

使い方は 2 つある:

1. **変換の途中で確認する。** 変換するスキル（またはレビューする人）は、下の各項目の「**出たら確認**」を見て、
   その生成物が出ていれば問いを投げ、答えを「**記録先**」に書く。答えが出るまで、その項目は未決のまま残す
2. **業務ロジックとの整合を取る。** 生成コードは Oracle と同じ結果を目指すが、移行先の都合で**意味が少し
   変わる**ところがある（§2）。変わったことを業務側が受け入れられるかは、業務の担当者にしか答えられない

各項目の ID は安定させてある。記録するときは ID で引く。

---

## 0. 確認の進め方

### 0.1 項目が「出た」かの見分け方

| 生成物・記録 | 出たら確認する項目 |
|---|---|
| `application/TriggerChecks.java` / `TriggerCheckJob.java` | OPS-1〜OPS-5 |
| `db/restrict-direct-writes.sql` | OPS-6〜OPS-10 |
| `db/trigger-check-baseline.sql` | OPS-4（削除との順序） |
| `<routine>Targets` / `One` / `Failed` / `Start` / `Done` / `FailedBatch`（割った routine） | CALL-1〜CALL-3、BIZ-1、BIZ-2 |
| `<routine>After` と `pAfterKey` / `pBatch` 引数（件数つきで繰り返し読む） | CALL-3、BIZ-2 |
| 生成コードのコメント `tx.runSeparately(...)`（自律トランザクション） | CALL-4、BIZ-3 |
| 診断 `OPTIMISTIC` / `RMW_SPLIT` / `MERGE_SPLIT`（楽観制御へ移したもの） | CALL-5、BIZ-4、BIZ-5 |
| `AuditContext audit` 引数 | CALL-6、BIZ-6 |
| `limits.yaml` の `scanRows.routines` の値 | BIZ-7 |
| `limits.yaml` の `dynamicTables` | BIZ-8 |
| 診断 `TRIGGER_APPLIED` / `TRIGGER_CALL`（書き込む側が trigger を呼ぶ） | OPS-6、BIZ-9 |
| 診断 `TRIGGER_REDESIGN`（値を書き換える trigger）、または `TriggerChecks` の C 型（採番）の照合 | BIZ-10 |
| TIMESTAMP WITH TIME ZONE の列（ScalarDB の `TIMESTAMPTZ`） | BIZ-11 |
| `TRUNCATE` を含む動的 SQL | BIZ-12 |

### 0.2 記録の形

どの項目も、答えは次の形で残す。**答えた人がいない項目を「決めた」と書かない。**

| 欄 | 中身 |
|---|---|
| ID | 下の項目の ID（例: `OPS-2`） |
| 状態 | 未決 / 決定 / 対象外（出ていない） |
| 決定 | 選んだ選択肢と、その理由 1〜2 行 |
| 決めた人 | 役割（業務担当・運用担当・他システム担当など） |
| 日付 | 決めた日 |
| 記録先 | 下の各項目の「記録先」。設定ファイルに書けるものはそこへ、書けないものは issue / 設計文書へ |

## 1. 運用で決めること（OPS）

### trigger の照合（#12 §0「検証で追う」）

移行先に trigger は無い。掛かるのは生成したコードが書くときだけで、PL/SQL の外（他システムの直接 DML、手作業の
保守 SQL、バッチ / ETL）からの書き込みには掛からない。**その穴は塞がず、照合で追う**と決めてある。照合そのもの
（`TriggerChecks`）と、回し方の雛形（`TriggerCheckJob`）は生成される。

#### OPS-1 照合をどこで回すか

| 選択肢 | 形 | 代償 |
|---|---|---|
| **a. アプリの外の定期ジョブ**（推奨） | Kubernetes の CronJob などから `TriggerCheckJob` を呼ぶ | ジョブの配備と監視が 1 つ増える |
| b. アプリの中で回す | アプリ内のスケジューラ | 全件を読む重い処理が業務と同じプロセスで動く。複数台で重複して走る |
| c. ScalarDB Analytics で回す | 照合を分析側の SQL に移す | 生成した Java が使えず、書き直しになる |

- **出たら確認**: `TriggerCheckJob.java`
- **記録先**: 運用設計書

#### OPS-2 実行時刻と間隔

- 間隔は決めてある: A（監査）・C（採番）は**日次**、B（拒否）・D（別表を読む検証）は**短い間隔**（既定 1 時間）。
  `TriggerChecks.INTERVALS` に書いてある
- 決めるのは**時刻**である。照合は表を全件読むので、日次は業務の閑散時間に置く
- 短い間隔の照合（`products` / `payments` の全件）が、本番の件数で間隔の中に収まるかを測る
- **出たら確認**: `TriggerChecks.INTERVALS`
- **記録先**: 運用設計書（ジョブの定義）

#### OPS-3 見つけたずれを誰がどう扱うか

| 型 | 生成物がすること | 運用で決めること |
|---|---|---|
| A 監査 | `TriggerCheckJob.daily` が補う（書いた主体 `BACKFILL`） | 自動で補ってよいか、人が確認してから補うか |
| B 拒否 / D 別表検証 | 見つけて返すだけ | **通知先**、対応期限、判断の結果（値を戻す / そのままにする）の記録先 |
| C 採番 | 使われているキーの最大値を返すだけ | 採番の次の値を先へ進めるのを自動にするか |

- 照合は状態を持たないので、**同じずれが毎回報告される**。対応済みの印をどこに持つか（控えの表に足す、別の表を持つ）
  も決める
- **出たら確認**: `TriggerCheckJob.Report`
- **記録先**: 運用設計書（障害対応の手順）

#### OPS-4 監査の削除との順序

- **日次の照合は、監査の削除（`prc_purge_audit`）より先に回す。** 逆にすると、消えた監査行の値が控えの表
  （`trigger_check_baseline`）に残らず、しばらく変わっていない行が照合から外れる（B 型の拒否条件も同時に外れる）
- 控えの表は移行で足す表である。移行先に `db/trigger-check-baseline.sql` で作っておく
- **出たら確認**: `db/trigger-check-baseline.sql` と、割った `prc_purge_audit`
- **記録先**: 運用設計書（ジョブの依存関係）

#### OPS-5 照合のトランザクションと失敗時

- 生成物の既定: 照合は読み取り専用トランザクション（`setReadOnly(true)`）、補完と控えの更新は別々の書き込み
  トランザクション。読み取りが衝突で弾かれたら 3 回まで読み直す
- 決めるのは、**ジョブ全体が失敗したときの再実行の方針**（次の回を待つか、すぐ再実行するか、誰に知らせるか）
- **記録先**: 運用設計書

### 直接の書き込みを権限で禁じる（#12 §0 の決定 3）

B（拒否）/ D（別表検証）の trigger が掛かる表は、アプリ以外からの書き込みを権限で禁じると決めてある。雛形は
`db/restrict-direct-writes.sql`（`REVOKE INSERT, UPDATE, DELETE ... FROM <other_user>`）。

#### OPS-6 `<other_user>` は誰か

- アプリ以外で対象の表に書いている利用者を数え上げる（他システム・手作業の保守・バッチ / ETL）
- 推奨: 書き込みはアプリの利用者だけにし、それ以外は読み取りだけにする
- **出たら確認**: `db/restrict-direct-writes.sql`
- **記録先**: 権限設計書

#### OPS-7 認証・認可を有効にする影響

- `REVOKE` が効くのは ScalarDB Cluster の認証・認可が有効なときだけである
- 有効にすると**すべてのクライアントに資格情報が要る**。アプリ・照合ジョブ・運用ツールの接続設定の変更を洗い出す
- **記録先**: 権限設計書、各クライアントの接続設定

#### OPS-8 権限は表単位である

- 守りたいのが 1 列（例: `products.unit_price` の値下げ幅）でも、`REVOKE` は表全体の書き込みを止める
- **他システムが同じ表の別の列（例: 在庫 `stock_qty`）を直接書いているなら、それも止まる。** その場合はその
  書き込みもアプリの API を通すか、列を別の表に分ける（スキーマの再設計）
- **記録先**: 権限設計書、他システムとの接続仕様

#### OPS-9 ScalarDB の下の DB の権限

- ScalarDB を通らずに下の RDBMS へ直接書く経路は、ScalarDB の権限の外にある。この経路は ScalarDB のトランザクション
  管理用の列も壊すので、どのみち禁じるべきである
- 推奨: 下の DB は、ScalarDB のサービス用アカウント以外を読み取りだけにする
- **記録先**: 権限設計書

#### OPS-10 緊急時の修正の経路

| 選択肢 | 形 | 代償 |
|---|---|---|
| **a. アプリに保守用の操作を用意する**（推奨） | trigger と同じ検証・監査を通る | 操作を作る手間 |
| b. 一時的に権限を与える手順 | 直接書く | 照合で B / D として検出される。手順と記録が要る |

- **記録先**: 運用設計書（障害対応の手順）

## 2. 呼び出し側で決めること（CALL）

生成コードは**トランザクションを開始も commit もしない**（計画 §9）。境界・再試行・並列度は呼び出し側の設計で
ある。生成コードには「回し方の出発点」がコメントとして出るが、**出発点であって決定ではない**。

#### CALL-1 割った routine の回し方（1 反復 = 1 トランザクション）

- 対象: `limits.yaml` の `transactions.perIteration` に書いた routine（`<routine>Targets` / `One` / `Failed` ...）
- 決めること: **再試行**（弾かれた 1 反復を何回やり直すか）、**並列度**（1 反復を並べて回してよいか）、
  **中断と再開**（途中で落ちたときにどこから再開するか）
- **出たら確認**: `<routine>One`
- **記録先**: 呼び出し側の設計書

#### CALL-2 全体の失敗の扱い

- `<routine>FailedBatch` が出ている routine は、全体が失敗したときに `batch_control` などへ記録を書く部品を持つ。
  **いつそれを呼ぶか**（どの失敗を「全体の失敗」とみなすか）を決める
- **出たら確認**: `<routine>FailedBatch`

#### CALL-3 1 回に取る件数（`pBatch`）

- 処理対象を件数つきで繰り返し読む routine は、`pBatch`（1 回に取る件数）を呼び出し側が渡す。**業務の数では
  なく運用の調整値**である。1 トランザクションの大きさとメモリ、1 ページあたりの往復回数の釣り合いで決める
- **出たら確認**: `Targets(..., BigDecimal pAfterKey, Integer pBatch)`
- **記録先**: 呼び出し側の設定

#### CALL-4 自律トランザクションの呼び方

- `transactions.separate` に書いた routine（例: `prc_audit_autonomous`）は、**呼び出し側のトランザクションとは
  別の境界で**呼ぶ。同じ中で呼ぶと、親が rollback したときに一緒に消える（Oracle では消えなかった）
- 決めること: どこで別の境界を開くか（呼び出し元ごと）
- **出たら確認**: コメント `tx.runSeparately(...)`

#### CALL-5 楽観制御で弾かれたときの再試行

- 行ロックを落として楽観制御へ移した routine（`rowLocks.optimistic`）は、衝突すると commit で弾かれる
- 決めること: 最大再試行回数、待ち時間、**その操作が冪等か**（採番や外部通知が同じトランザクションにあると、
  再試行は二重実行になる）、**業務例外と衝突を区別できるか**（例: 在庫不足 -20030 は再試行しても変わらない）
- **出たら確認**: 診断 `OPTIMISTIC` / `RMW_SPLIT` / `MERGE_SPLIT`
- **記録先**: `limits.yaml` の `rowLocks.optimistic` の理由欄、呼び出し側の設計書

#### CALL-6 誰が・いつを渡すか（`AuditContext`）

- Oracle の `USER` / `SYSTIMESTAMP` は、呼び出し側が `AuditContext` として渡す（#1・#8）。`USER` はデータベースの
  セッションの利用者であって、アプリの利用者ではない
- 決めること: `user()` に何を入れるか（ログインした利用者・サービス名・代行者など）、`now()` にどの時計を使うか
- **出たら確認**: `AuditContext audit` 引数
- **記録先**: 呼び出し側の設計書

## 3. 業務ロジックとの整合（BIZ）

生成コードは Oracle と同じ結果を目指すが、**移行先の都合で意味が変わるところ**がある。どれも比較ハーネスでは
「一致」に見えることがある——**変わったのは、シナリオが観測していない部分**だからである。業務の担当者に、
変わったことを受け入れられるかを確かめる。

#### BIZ-1 1 反復 = 1 トランザクションにしたことで、全体の原子性が無くなる

- Oracle では、routine 全体（または中間コミットまでの単位）が 1 つの境界だった。割った後は、**途中までが確定し、
  残りが未処理のまま**という状態がありうる
- 聞くこと: その状態で業務が困るか（例: 締め処理の途中で止まったとき、確定分だけで帳票を出してよいか）
- 対象: `nightly_close` / `purge_audit` / `reprice_all` / `mark_reviewed` / `restock` など `transactions.perIteration`

#### BIZ-2 処理対象を読んだ時点と、処理する時点がずれる

- 処理対象は 1 反復とは別のトランザクションで、**ページごとに**読む。Oracle は OPEN の時点の集合を回していた
- 変わること: 処理の途中で**追加された行も処理される**（キーが先にあるもの）。読んでから処理するまでの間に
  **条件から外れた行**は、1 反復の側で確かめないと処理されてしまう
- 聞くこと: 途中で追加された行を同じ実行で処理してよいか。1 反復が自分で状態を確かめているか（例: `SHIPPED` の
  注文だけを `CLOSED` にする、という遷移がそれを持っている）

#### BIZ-3 自律トランザクションの記録

- `prc_audit_autonomous` のような「親が失敗しても残る記録」は、呼び出し側が別の境界で呼ばない限り残らない（CALL-4）
- 聞くこと: 失敗の記録が残らない経路が無いか（呼び出し元をすべて洗う）

#### BIZ-4 行ロックが無くなり、衝突が分かるタイミングが変わる

- Oracle は読んだ瞬間に待つ・弾く（`FOR UPDATE` / `NOWAIT`）。移行先は **commit のときに**弾く
- 変わること: `NOWAIT` の失敗（-20031 など）を業務判断に使っていた呼び出し側は、その判断が commit 時点まで
  遅れる。`SKIP LOCKED` で取り合っていた処理（`claim_batch`）は、「飛ばす」が「弾かれて再試行」になる
- 聞くこと: 待たずに諦めることに業務上の意味があったか

#### BIZ-5 MERGE を「読んでから選ぶ」に割った

- 既存行なら `WHEN MATCHED` の列だけを更新し、無ければ挿入する（UPSERT で他の列まで上書きしないため）
- 変わること: 同じキーを同時に書くと、片方が commit で弾かれる
- 聞くこと: 同じキーへの同時書き込みが業務上起こるか。起こるなら、弾かれた側の再試行が正しいか

#### BIZ-6 監査に残る「誰が」

- `changed_by` は `AuditContext.user()` から入る（CALL-6）。移行前はデータベースの利用者名だった
- 補った監査行（OPS-3）は、書いた主体が `BACKFILL`、時刻が補った時刻になる——**元の「誰が」「いつ」は分からない**
- 聞くこと: 監査要件（法令・内部統制）として、この 2 つが許されるか

#### BIZ-7 行数の上限の値

- 行を先に全部読む routine には、上限を超えたら止まる仕組みがある。値は業務の数である
  （例: 1 注文あたりの明細数 200 を超える注文は、業務側で確認すべき異常とみなす）
- 聞くこと: その値を超える入力が業務上ありうるか。ありうるなら、止まることが正しいか
- **記録先**: `limits.yaml` の `scanRows.routines`（理由をコメントに）

#### BIZ-8 動的 SQL が受け付ける表名

- 表名が実行時に決まる動的 SQL は、**`dynamicTables` に書いた表名だけ**を受け付け、それ以外は実行時に拒否する。
  Oracle ではどの表でも走った
- 聞くこと: 呼び出し側が渡しうる表名はどれか。一覧に無い表名で呼ばれる経路が無いか
  （例: `truncate_staging` の一覧は corpus のシナリオに合わせて `inventory_tx` にしてある——名前は staging だが、
  staging 用の表は schema に無い。移行先で staging 表を作るなら、その名前を足す）
- **記録先**: `limits.yaml` の `dynamicTables`

#### BIZ-9 trigger が掛かるのは生成コードの経路だけ

- 生成コードが書く経路には trigger が掛かる（書き込む側が trigger の本体を呼ぶ）。PL/SQL の外から書く経路には
  掛からない（OPS-1〜OPS-10 で追う・塞ぐ）
- 聞くこと: 対象の表に、PL/SQL 以外から書いている業務があるか。あるなら、その書き込みもアプリの API を通すか、
  照合で検出される前提で運用するか

#### BIZ-10 値を書き換える trigger（採番 trigger）

- `:NEW.order_id := seq.NEXTVAL` のような trigger は、呼び出しでは置き換えられない（採番 Service への再設計）
- 聞くこと: キーを渡さずに INSERT している業務はどれか。その業務が採番 Service を呼ぶ形に変えられるか。
  注文番号の**欠番・順序**に業務上の意味があるか（採番方式の選択に効く）

#### BIZ-11 タイムゾーンつきの時刻の offset が失われる

- Oracle の TIMESTAMP WITH TIME ZONE は瞬間と offset の両方を持つが、ScalarDB の `TIMESTAMPTZ` は瞬間だけを
  持つ。読み戻すと同じ瞬間の UTC 表記になる。比較・並べ替え・差は変わらない
- 聞くこと: offset から「どの地域で記録されたか」を読んでいる業務があるか

#### BIZ-12 TRUNCATE が直前の作業を commit しない

- Oracle の `TRUNCATE` は DDL で、直前の作業ごと暗黙に commit する。ScalarDB では直前の作業は commit されない
  （TRUNCATE 自体が rollback で戻らないのは同じ）
- 聞くこと: TRUNCATE の前に書いた内容が、TRUNCATE の時点で確定していることに依存している業務があるか

## 4. この文書の保守

- 新しい決定・新しい生成物が増えたら、§0.1 の対応表と該当する節に項目を足す。ID は振り直さない
- §0.1 の表は `skills/plsql-migrate/scripts/decision_items.py` が読む。行を足したら、その行の見分け方
  （`DETECTORS`）も足す。見分け方の無い行があるとスクリプトは失敗する——黙って飛ばすと、その項目は
  確認されないまま残る
- 文ごとの診断コード（`ROW_LOCK`、`RMW_SPLIT` など）を足したら、`skills/plsql-migrate/scripts/migration_doc.py` の
  `CHANGES` に「意味が変わる / 形が変わる / 情報」の分類を足す。分類が無いと変換後の文書に「未分類」と出て、
  corpus に未分類があるとテストが落ちる
