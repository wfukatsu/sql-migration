# sql-transpile の課題と解決方法の調査

作成日: 2026-09-11
関連文書: `skills/sql-transpile/SKILL.md`（スキル本体）、`out/transpile-verify/report.md`（実行検証の結果）

このスキルの実行検証で見つかった課題について、解決方法を調べて試作し、効果を実測した結果をまとめる。スキル本体はまだ変更していない。

---

## 1. 課題の整理

実行検証では、Oracle・PostgreSQL・MySQL を変換元とし、変換先 3 つずつの計 9 通り、321 の文と変換先の組を実データベースで動かした。

| 指標 | 値 |
|---|---|
| スキルが変換後の SQL を出した割合 | 88.2% |
| OK 判定が実際に正しかった割合 | 80.4% |
| 見逃し（OK と判定したのに失敗、または結果が違う） | 48 |

見逃しは原因で 3 つに分かれる。

| 原因 | 件数 |
|---|---|
| 変換先に無い構文をそのまま通す | 34 |
| 既存の検出や変換の不具合 | 7 |
| 型や照合順序による意味の差 | 7 |

このほかに、判定を誤らせる問題がある。コメント中の単語による誤検出、関数の移植性チェックの低い精度、変換先が持つ構文まで拒否する過剰な拒否である。

---

## 2. 結論

対策は 4 層に分けて重ねるのがよい。上の層ほどデータベース無しで動き、下の層ほど一般性が高い。

| 層 | 対策 | 見逃し 48 件への効果 | 誤警報 | 変換先のデータベース |
|---|---|---|---|---|
| 1 | 個別の変換不具合を直す | 約 21 件が正しい変換に変わる見込み | — | 不要 |
| 2 | 変換先の能力表で検出する | 38 件を検出 | 218 件中 2 件 | 不要 |
| 3 | 変換先で EXPLAIN をかけて検証する | 39 件を検出 | 218 件中 0 件 | 必要。表定義だけでよい |
| 4 | 型情報で意味の差を解消する | 残り 8 件のうち 5 件が正しい変換に変わる | — | 不要。表定義は要る |

層 2 と層 3 を合わせると 40 件を拾う。どちらでも拾えない 8 件は、すべて型や照合順序による意味の差で、層 4 の対象になる。そのうち照合順序による 3 件は、テキストだけでは完全には直せないので警告にとどめる。

判定の精度は、これとは別に直す。コメントによる誤検出は構文木での判定に、関数の移植性はデータベースの関数一覧に基づく判定に置き換える。詳細は第 6 節。

## 3. 変換先で動かない構文をどう見つけるか

### 3.1 変換先で EXPLAIN をかける

スキルが出した SQL を、変換先のデータベースに実行させずに解析だけさせる。PostgreSQL・MySQL・DuckDB は `EXPLAIN`、Oracle は `EXPLAIN PLAN FOR` を使う。DDL は解析できないので、トランザクション内で実行して取り消す。

| 変換元 | 変換先 | 出力した文 | 実際に壊れていた文 | EXPLAIN で検出 | うち見逃し | 見逃しの検出 | 誤警報 |
|---|---|---|---|---|---|---|---|
| Oracle | PostgreSQL | 47 | 7 | 5 | 4 | 4 | 0 |
| Oracle | MySQL | 45 | 10 | 9 | 6 | 6 | 0 |
| Oracle | DuckDB | 47 | 6 | 5 | 4 | 4 | 0 |
| PostgreSQL | Oracle | 25 | 11 | 9 | 10 | 8 | 0 |
| PostgreSQL | MySQL | 25 | 7 | 5 | 7 | 5 | 0 |
| PostgreSQL | DuckDB | 24 | 2 | 1 | 2 | 1 | 0 |
| MySQL | Oracle | 23 | 12 | 10 | 7 | 5 | 0 |
| MySQL | PostgreSQL | 24 | 5 | 4 | 4 | 3 | 0 |
| MySQL | DuckDB | 23 | 5 | 4 | 4 | 3 | 0 |
| **合計** | | **283** | **65** | **52** | **48** | **39** | **0** |

- **誤警報がゼロ。** 実際に正しく動いた 218 文で、EXPLAIN が誤ってエラーを出したことは一度もない。
- **必要なのは表定義だけで、データは要らない。** スキルが変換した CREATE TABLE は全変換先で通ったので、変換対象の DDL から検証用の表をそのまま作れる。
- **拾えないのは、動くが結果が違う文。** 整数の除算や大文字小文字の扱いの差は、構文としては正しいので EXPLAIN を通る。Oracle の日付リテラルの失敗も、実行時の型変換で起きるため EXPLAIN では出ない。

スキルへの組み込みは、変換先の接続先を渡したときだけ動く任意の検証段にするのがよい。使い捨てのスキーマかトランザクションの中で表を作り、各文を EXPLAIN して、失敗した文を ERROR に格上げする。

### 3.2 本物のパーサーをオフラインで使う

PostgreSQL は、本物の文法解析器を Python から使える pglast がある。Python 3.14 と Apple Silicon 向けの配布物もあり、データベース無しで動く。

| 対象 | 結果 |
|---|---|
| PostgreSQL を変換先にした見逃し | 8 件中 3 件を検出 |
| 正しく動いた文での誤警報 | 59 件中 0 件 |

拾えたのは MySQL 固有の `WITH ROLLUP`、結合つき UPDATE、ORDER BY と LIMIT つき UPDATE で、どれも純粋な構文エラーである。FROM dual や RECURSIVE の欠落のような名前解決のエラーは拾えない。軽い第一段として有効だが、EXPLAIN の代わりにはならない。

MySQL と Oracle には、オフラインで使える本物の文法解析器が見当たらない。DuckDB は変換先そのものがプロセス内で動くので、変換した表定義を作ってから EXPLAIN すれば、データベース無しで第 3.1 節と同じ検証ができる。

### 3.3 変換先の能力表

変換先ごとに持っていない構文を表にし、スキルの出力を調べる。試作して検証データで採点した。

| 結果 | 値 |
|---|---|
| 見逃しの検出 | 48 件中 38 件 |
| 正しく動いた文での誤警報 | 218 件中 2 件 |

**誤警報の 2 件は、どちらも手で書いた能力表の誤りだった。** Oracle 23ai は集約の FILTER 句を受け付け、MySQL は SERIAL を型の別名として受け付ける。能力表はデータベースのバージョンで変わり、書き間違えやすい。この 38 件という数字は、見逃しを見てから規則を書いたので楽観的でもある。

**SQLGlot の組み込みフラグでは能力表を置き換えられない。** 生成器には能力を表すフラグが 25 個あるが、見逃しの原因になった MERGE・ROLLUP・FILTER・SERIAL・DUAL・ON CONFLICT に対応するものは無い。使えるのは次の 4 つにとどまる。

- `CTE_RECURSIVE_KEYWORD_REQUIRED`: どの方言が再帰 CTE に RECURSIVE を要求するか
- `UPDATE_STATEMENT_SUPPORTS_FROM`: UPDATE で FROM 句を使えるか
- `RETURNING_END`: RETURNING を文末に置くか
- `DUPLICATE_KEY_UPDATE_WITH_SET`: MySQL 形式の upsert の書き方

能力表は、よく出る既知の欠落を素早く拾う補助にとどめる。一般性は EXPLAIN に任せる。

## 4. 個別の変換不具合と直し方

10 件それぞれについて原因を特定し、直し方を試作して実データベースで確かめた。

| # | 不具合 | 原因 | 直す場所 | 検証 | SQLGlot への還元 |
|---|---|---|---|---|---|
| 1 | 再帰 CTE の RECURSIVE の有無 | スキルの不足 | スキルの前処理 | PostgreSQL・DuckDB・Oracle で結果一致 | 不要 |
| 2 | FROM dual が残る | スキルの不足 | スキルの前処理 | PostgreSQL・DuckDB・MySQL で結果一致 | 不要 |
| 3 | FROM 側に付いた外部結合の記号 | **スキルの不具合** | スキルの前処理 | DuckDB で Oracle と結果一致 | 推奨 |
| 4 | 日付リテラルが Oracle で失敗 | SQLGlot の生成器 | スキルの前処理で回避 | Oracle で結果一致 | 推奨 |
| 5 | MySQL の DIV が Oracle で四捨五入 | SQLGlot の生成器 | スキルの前処理で回避 | Oracle で結果一致 | 推奨 |
| 6 | バッククォートが Oracle で大文字小文字を区別 | SQLGlot の意味の扱い | スキルの前処理 | Oracle で結果一致 | 不要 |
| 7 | DISTINCT ON が Oracle で失敗 | SQLGlot の生成器 | スキルの前処理で回避 | Oracle で結果一致 | 推奨 |
| 8 | INTERVAL の複数形が Oracle で失敗 | SQLGlot の生成器 | スキルの前処理 | Oracle で PostgreSQL と結果一致 | 一部推奨 |
| 9 | ScalarDB で日付リテラルを拒否 | 本体の変換器 | 本体を直して同梱を更新 | ERROR が WARN になり変換される | 不要 |
| 10 | TRUNC の単位が正規化されない | SQLGlot の生成器 | スキルの前処理で回避 | PostgreSQL・DuckDB・MySQL で結果一致 | 推奨 |

### 4.1 各不具合の要点

1. **再帰 CTE。** SQLGlot の With ノードは recursive という属性を持つが、Oracle は RECURSIVE を書かないので立たない。本体を自分自身の名前で参照する CTE を見つけたら、変換先が RECURSIVE を要求する場合に属性を立てる。Oracle が変換先なら属性を外し、Oracle が要求する列名の並びを補う。互いに参照し合う複数の CTE は検出できない。
2. **FROM dual。** 変換先が Oracle でなく、FROM が修飾の無い DUAL だけのときに FROM 句ごと落とす。どの変換先も FROM の無い SELECT を受け付ける。MySQL は DUAL を持つが、SQLGlot が引用符で囲むので表として解決されずに失敗する。定数を元にした MERGE も、この処置で PostgreSQL で動くようになった。
3. **FROM 側に付いた外部結合の記号。** 検出関数は、書き換えが残す重複した別名や CROSS JOIN を探す。ところがスキルは書き換えの**前**に呼んでいるので、必ず偽を返す。本体は書き換えの後に呼んでおり、こちらが正しい。最低限は呼ぶ位置を直して拒否すればよい。より良いのは、書き換えの前に FROM の表を記号の付いていない表と入れ替え、保持される側を先頭に置くことで、これで正しく変換できる。3 表以上で記号の向きが混ざる形は未検証。
4. **日付リテラル。** PostgreSQL と MySQL の日付リテラルは、SQLGlot 内部で文字列の CAST として表される。Oracle の生成器はそのまま CAST を出し、既定の日付書式に依存して失敗する。変換先が Oracle なら、年月日の形の文字列の CAST を、書式を明示した TO_DATE に置き換える。タイムスタンプのリテラルにも同じ処置が要る。
5. **MySQL の DIV。** SQLGlot は整数除算を CAST で表し、Oracle の CAST は四捨五入する。変換先が Oracle なら TRUNC に置き換える。検証では MySQL と同じ値になった。
6. **バッククォート。** MySQL のバッククォートは大文字小文字に意味を持たないが、Oracle では大文字小文字を区別する二重引用符になる。変換元が MySQL なら、単純な識別子の引用符を外す。SQLGlot は Oracle の予約語の一覧を持たないので、ORDER や LEVEL のような語まで外してしまう。予約語の一覧をスキル側に持つ必要がある。
7. **DISTINCT ON。** SQLGlot の書き換えは、アンダースコアで始まる別名を作る。Oracle の生成器はこれを引用符で囲まないので失敗する。書き換えを前処理で適用し、アンダースコアで始まる識別子を別名に付け替える。
8. **INTERVAL。** SQLGlot は複数形の単位を残す。単数形に直すだけでは、月末の日付で Oracle が失敗する落とし穴がある。Oracle が変換先なら、月と年の加算は ADD_MONTHS に書き換える。月末の扱いが PostgreSQL と一致した。
9. **ScalarDB の日付リテラル。** Oracle の日付リテラルは SQLGlot 内部で専用のノードになるが、本体の変換器の値の検査がこのノードを受け付けていない。エラーに TO_DATE と出るのは、そのノードの表示形にすぎない。本体の値の検査にこのノードを加え、同梱コピーを更新する。
10. **TRUNC の単位。** Oracle の書式の単位がそのまま渡り、PostgreSQL と DuckDB は受け付けない。MySQL では日単位の切り捨てに化け、**結果が黙って変わる**。Oracle の書式を標準の単位名に写像し、文字列リテラルとして渡す。MySQL でも月初の日付になることを確かめた。

### 4.2 SQLGlot への還元

4・5・7・8 の複数形・10 と、3 の書き換えが表を重複させる問題は、SQLGlot 本体の不具合である。本体に報告して直してもらうのが根本解決になる。それまではスキルの前処理で回避できる。

## 5. 型や照合順序による意味の差

### 5.1 整数どうしの除算

PostgreSQL は整数どうしの除算で小数部を切り捨てる。Oracle・MySQL・DuckDB は小数を返す。SQLGlot は列の型を知らないと、この差を埋められない。

SQLGlot の最適化器で、表定義から列を解決し、型を付けてから生成すると、SQLGlot は整数除算の模倣を出す。ただしその模倣は CAST で、**切り捨てではなく四捨五入になるので誤り**である。

| 式 | PostgreSQL（正解） | Oracle | MySQL | DuckDB |
|---|---|---|---|---|
| 7499 / 4 を整数で | 1874 | 1874.75 | 1874.75 | 1874.75 |
| SQLGlot の CAST による模倣 | — | 1875 | 1875 | 1875 |
| -7 / 2 を CAST で模倣 | -3 | -4 | -4 | -4 |
| 正しい模倣 | — | TRUNC で割る | DIV 演算子 | `//` 演算子 |

正しい模倣では、どの変換先でも 1874 と -3 になり、PostgreSQL と一致した。

実装の注意が 2 点ある。

- **型付けには列の解決が要る。** 型付けだけを行うと列の型が不明のままになる。列の解決を先に行う必要がある。
- **列の解決は出力を書き換えてしまう。** 表名の修飾や別名が付くので、型の判定は複製した構文木で行い、書き換えは元の構文木に施す。

表定義が無いときは、変換元が整数除算の方言で、被演算子の型が分からない除算を WARN にする。

MySQL の DIV を変換元にした場合は、DuckDB の `//` と PostgreSQL の DIV 関数が正しく、Oracle だけ TRUNC への書き換えが要る。第 4 節の 5 と同じ処置である。

### 5.2 日付どうしの差

PostgreSQL の日付どうしの差は日数を返す。Oracle と DuckDB も同じ式で日数を返し、正しく動く。MySQL だけは、日付を数値として引き算して意味の無い値を返す。

| 変換先 | そのままの式 | DATEDIFF |
|---|---|---|
| Oracle | 3302（正しい） | 使えない |
| DuckDB | 3302（正しい） | — |
| MySQL | 98884（誤り） | 3302（正しい） |

型付けをしても出力は変わらなかった。変換先が MySQL のときだけ、日付どうしの差を DATEDIFF に書き換える。SQLGlot の DATEDIFF ノードは MySQL には正しく出るが Oracle には誤った形で出るので、書き換えは MySQL に限る。

### 5.3 MySQL の大文字小文字を区別しない比較

MySQL の既定の照合順序では、LIKE も等号も大文字小文字を区別しない。`'KING' LIKE 'k%'` も `'KING' = 'king'` も真になる。PostgreSQL・Oracle・DuckDB ではどちらも偽になる。

書き換えの手段はある。

| 手段 | 使える変換先 |
|---|---|
| ILIKE | PostgreSQL・DuckDB |
| 両辺を LOWER で囲む | すべて |
| COLLATE BINARY_CI | Oracle 23ai |
| COLLATE NOCASE | DuckDB |
| 大文字小文字を無視する正規表現 | すべて |

SQLGlot は、ILIKE を Oracle と MySQL 向けには両辺を LOWER で囲む形で出す。

**書き換えには索引の犠牲がある。** PostgreSQL で確かめると、等号の検索は索引を使ったが、ILIKE と LOWER を使った検索は全件走査になった。式索引か三文字組の索引を別に用意する必要がある。

**SQL の文面だけでは完全には直せない。** 大文字小文字の扱いは、LIKE だけでなく等号・IN・GROUP BY・DISTINCT・一意性制約にも及ぶ。しかも照合順序は列ごとに決まり、大文字小文字を区別する列もありうるので、文面からは判断できない。

既定では、変換元が MySQL で変換先が大文字小文字を区別する場合に、文字列の比較を WARN にする。利用者が選んだときだけ、ILIKE か LOWER を使う形に書き換える。その場合は索引の犠牲も併せて伝える。

## 6. 判定の精度

### 6.1 コメントによる誤検出

今の残存構文チェックは、コメントを含む出力の文字列を正規表現で調べている。そのため、ふつうのコメントで誤って ERROR になる。

| 入力 | 今のスキル | コメントを除いて正規表現 | 構文木で判定 |
|---|---|---|---|
| `-- process prior orders first` | 誤って ERROR | 正しい | 正しい |
| `-- keep ROWNUM semantics` | 誤って ERROR | 正しい | 正しい |
| 引用符で囲んだ列名 "rownum" | 誤って検出 | 誤って検出 | 正しい |
| PIVOT を PostgreSQL へ | 検出 | **見逃す** | 正しい |
| 否定 5 件と肯定 9 件の計 14 件 | — | — | **14 件すべて正しい** |

コメントを除くだけでは足りない。PostgreSQL 向けにふつうに生成すると、SQLGlot は PIVOT 句を黙って丸ごと消す。今のスキルが PIVOT を拾えているのは、例外を出す生成のおかげにすぎない。

構文木で判定すれば、コメント・文字列リテラル・引用符で囲んだ列名に惑わされない。各構文は SQLGlot で次のノードになる。

| 構文 | SQLGlot のノード |
|---|---|
| CONNECT BY・START WITH | Connect |
| PRIOR | Prior |
| LEVEL・ROWNUM・ROWID | 引用符の無い名前の Column |
| SYS_CONNECT_BY_PATH | 名前の付いた未知の関数 |
| PIVOT・UNPIVOT | Pivot。UNPIVOT は属性で区別 |
| KEEP | 種別が KEEP の Window |
| NEXTVAL・CURRVAL | その名前の Column。表の位置にシーケンス名 |
| ヒント | SELECT に付く Hint |

引用符の有無は、識別子の quoted 属性で見分ける。残存構文チェックは、前処理後の変換元の構文木に対するこの判定に置き換える。文字列で調べる処理が残る場合は、コメントを出さずに生成した文字列を使う。

### 6.2 関数の移植性チェック

今のチェックは、変換元の関数名がそのまま出力に残ったら要確認とする。検証では、この警告のうち実際に壊れていたのは 32 件中 11 件、34% だった。標準 SQL の EXTRACT まで警告し、逆に generate_series は、SQLGlot の内部名と出力名が違うため見逃している。

各データベースの組み込み関数の一覧を抜き出し、それに照らして判定する方法を試した。

| データベース | 抜き出し元 | 関数名の数 |
|---|---|---|
| DuckDB | duckdb_functions() | 945 |
| PostgreSQL | pg_proc の pg_catalog 分 | 2694 |
| Oracle | V$SQLFN_METADATA と SYS.STANDARD | 1349 |
| MySQL | mysql.help_topic の関数と演算子 | 416 |

変換後の SQL の構文木から関数名を取り、変換先の一覧にあるかを見る。EXTRACT・CAST・TRIM・SUBSTRING のような構文扱いの関数は対応済みとみなす。

| 判定方法 | 警告が当たった割合 | 壊れた文を拾えた割合 | 誤警報 |
|---|---|---|---|
| 今の方式（名前が残るか） | 34% | generate_series を見逃す | 21 件 |
| 関数一覧による判定 | **100%** | 69.2% | **出力した 283 文すべてで 0 件** |

関数一覧による判定は、generate_series を Oracle と MySQL で拾い、DuckDB では正しく拾わない。

拾えない壊れ方が 2 種類ある。

- **引数の誤り。** TRUNC に渡す単位 'MM' や、DATEDIFF の引数の数は、関数名の一覧では判定できない。既知の関数に対する引数の規則を別に持つ。
- **表示の食い違い。** SQLGlot は MySQL の TRUNC を TRUNCATE と表示し直すので、一覧にある TRUNCATE として通ってしまう。関数名は、出力した文字列上の実際の綴りから取る。

出力の文字列を単純な単語として走査する方法も試したが、拾える割合は上がる代わりに誤警報が 13 件出た。表名や型名まで関数と見なすためで、採らない。

関数一覧は JSON としてスキルに同梱し、一覧のある変換先ではそれに基づいて判定する。一覧の無い変換先では、今の方式に戻す。一覧はデータベースのバージョンに依存するので、抜き出した版を記録し、上記の抜き出し元から作り直せるようにしておく。今回の版は PostgreSQL 16、Oracle Database 23ai Free、MySQL 8.4、DuckDB 1.5.5 である。

### 6.3 過剰な拒否

CREATE SEQUENCE・PIVOT・DISTINCT ON は、変換元を基準にした規則で一律に ERROR にしている。実際には PostgreSQL・DuckDB・Oracle はシーケンスを持ち、DuckDB は PIVOT と DISTINCT ON を持つ。

DISTINCT ON の件は、規則の設計の誤りをはっきり示している。SQLGlot は、変換先が DISTINCT ON を持たないときは自分で書き換える。そのため出力に DISTINCT ON が残るのは、変換先が持っているときに限られる。出力の文字列を調べる今の規則は、変換先が対応している場合にだけ ERROR を出していた。

変換元を基準にした規則を、変換先の能力を基準にした判定に置き換える必要がある。第 3.3 節の能力表と、第 6.1 節の構文木での判定を組み合わせる。

### 8.1 実装して分かったこと

調査の段階では見つかっていなかったもの。

- **SQLGlot の外部結合の書き換えは例外を投げることがある。** 保持される側の表を決められないと `AssertionError` になる。変換全体が止まらないよう、ERROR として報告する
- **Oracle の字句解析は `WITHIN GROUP (` の GROUP を名前として読む。** `ON CONFLICT (col)` も同じ形になる。関数一覧との照合から外した
- **DuckDB 向けには SQLGlot が CONNECT BY を再帰 CTE に書き換える。** 1 表の単純な形は実行して結果が一致した。`SYS_CONNECT_BY_PATH`・`CONNECT_BY_ISLEAF`・`ORDER SIBLINGS BY`・結合・`FROM dual` は失敗し、`NOCYCLE` は循環を検出しない。単純な形だけを通す
- **MySQL の `AUTO_INCREMENT` は Oracle 向けにそのまま出る。** `GENERATED BY DEFAULT AS IDENTITY` に書き換える
- **PostgreSQL の `nextval()` は DuckDB でも動くが、SERIAL が暗黙に作るシーケンスは DuckDB に無い。** WARN にする
- **MySQL の `DATEDIFF` は Oracle に無い。** 日付の引き算に書き換える
- **関数一覧との照合は、出力を読み直して表示し直すと誤る。** MySQL の `TRUNC` が `TRUNCATE` と表示し直されるなど綴りが変わるので、変換先の字句をそのまま見る

### 8.2 実装しなかったもの

- **変換先への EXPLAIN による検証段（第 7 節の 9）。** 変換先への接続を要する新機能なので、今回の不具合修正には含めなかった。修正後の見逃しは 0 件で、この検証用 SQL では EXPLAIN が追加で拾うものは無い
- **SQLGlot 本体への不具合報告（第 7 節の 11）。** 外部への投稿になるので行っていない。報告の候補は、外部結合の書き換えの FROM 先頭の扱いと例外、TRUNC の書式、Oracle 向け DISTINCT ON の別名、INTERVAL の複数形、MySQL の DIV の CAST、DUAL の引用、Oracle 向けの AUTO_INCREMENT

### 8.3 限界

- 100% は、3 方言の検証用 SQL（各 27〜53 文）と 9 ペアの範囲での値。検証用 SQL に無い構文の見逃しは測れていない
- 関数一覧は PostgreSQL 16、Oracle Database 23ai Free、MySQL 8.4、DuckDB 1.5.5 のもの。バージョンが違えば `build_catalogs.py` で作り直す
- 照合順序の判定は、列ごとの照合順序の設定を見ない
- 型に依存する書き換えは表定義が要る。無ければ WARN にとどまる
